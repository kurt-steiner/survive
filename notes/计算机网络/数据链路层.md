## 格式塔

![image](../images/计算机网络-第%201%20页.drawio.png)

网络层的数据交给 数据链路层，<span style="color: blue">进行封装成帧</span> 后，由数据链路层 发送到相邻节点  
这就好像在 两个仓库站点之间 进行数据传输，我们将整个过程拆解开来，有

1. <span style="color: red"> 组帧 </span> /**序列化**  
在相邻站点之间进行数据传输时，由于传输是用电信号进行传输，需要将数据进行编码，让对方站点能够通过一定规则读取到正确数据，这个编码过程叫作 **组帧**
2. <span style="color: red">流水线传输 </span>/车队运输  
一般简单的情况是，发送方发送一份数据，接收到对方的ACK后，再发送下一份数据；这个过程可以用流水线技术 对多个数据帧进行同时运输  
这个过程在教材上叫作 **流量控制与可靠运输**
3. <span style="color: red">介质访问控制 </span> /交通情况  
上面的过程我们可以用 车队 比喻流水线技术，既然是车队，就要开到公路上  
在公路上，有各种交通事故可能产生，比如撞车，追尾；当发生交通事故时，站点需要进行退避，一定时间后再进行传输任务
4. <span style="color: red">验收</span>/**反序列化**  
对方站点接受到数据后，需要通过一定的规则将数据进行解码，也就是对货物进行 验收  
如果验收没有通过，接受方要么不对这份货物进行回应，发送方在一段时间后会因为超时进行重传；要么直接告诉发送方数据出错

## 1. 组帧/数据序列化

![image](../images/组帧.png)

### a. 早期 ———— 字符计数 和 首位定界符/字符填充法

在网络发展早期，工程师采用 **字符计数** 的方式来进行组帧，数据由

1. 数据个数
2. 数据

构成，假如一个帧中有数据 `1234` ，加上 数据个数，一共5个数据，那帧将以 `51234` 的形式传输  
我们发现，只要有一个数据出错，后续的数据接连出错，**一步错，步步错**，现在这种方法基本不用
___
后来，工程师们用类似如下的形式来序列化帧

```
begin
    1234
    5678
end
```

用一个特殊的数据表示 `begin` ，即传输开始  
用一个特殊的数据表示 `end` ，即传输结束  
但是我们很快发现一个问题，如果传输的数据中，有和 `begin` 或 `end` 同样格式的数据 该怎么办？  
我们又拿出一个特殊的数据 `esc` 表示 转义，比如在数据中有和 `begin` 或 `end` 相同格式的数据，我们这样序列化数据

```
begin
    esc begin
    esc end
end
```

那如果和 `esc` 相同呢？再加一个 esc

```
begin
    esc esc
end
```

在接收端，这种特殊数据不会作为数据进行处理，这种方式叫做 **首尾定界符法**

### b. 主流 ———— 零比特填充法 和 违规编码法

在 **零比特填充法** 中，序列化数据时，如果连续遇到5个1，那就在后面添加一个0  
在 **违规编码法** 中，将 1 序列化成 高低电平，将 0 序列化成 低高电平，在接收时，如果发现有 **高高电平** 或是 **低低电平**，那就看作违规编码，不做其进行处理  
很明显，这种方法有强大的抗干扰能力，并且序列化方式极其简单

## 2. 流水线运输/车队运输

![image](../images/流水线运输.png)

### 2.1 停止等待 运输

在进行流水线运输的介绍前，我们先介绍 一种原始的运输模式 ———— 停止等待  
在发送方发送一份数据后，发送方会等待接收方的确认(ACK)，收到ACK后，再发送下一份数据

### 2.2 流水线运输

在进行流水线就运输时，需要确保目的地的数据**有序** 且 正确，因此我们需要对每一个**数据帧**进行编号，我们会在数据帧中取一定的比特位 存储序号  
由于数据帧的长度固定，比特位在其中的存储 寸土寸金，我们不能拿一个 `u64` 类型直接塞到数据帧里去  
于是，我们只取 $\text{bit}$ 位，序号从 $0 \sim 2^{bit} - 1$

流水线运输的模式有两种

1. <span style="color: blue">回退N帧</span>  
其中 发送方的窗口大小为 $n$，接收方的窗口大小为 $1$
2. <span style="color: blue">选择重传</span>  
其中 发送方的窗口大小为 $n$，接收方的窗口大小为 $m$

流水线模式下，由于序号是有周期的，当接收方 ACK 丢失或者 ACK 延迟了一点时间才到发送端 时，有可能造成序号虽然正确，但不是同一周期的序号  
好在我们可以控制**窗口的大小**来检查出 序号是否正确

#### 2.2.1 流水线模式1 —— 回退N帧 / GBN

现在我们取 $\text{3}$ 位用作帧序号，序号从 $0$ 到 $2^{3} - 1$，一个循环共 $2^{3}$ 个帧
___
我们设发送方的窗口大小为 $2^3 = 8$，在传输数据时，有
![image](../images/计算机网络-第%202%20页.drawio.png)

其中，接收方已经将窗口移动到 序号为7的帧，并进行**累积确认**，只发送了一个 **ACK7**，并将窗口向前移动，此时  
![image](../images/计算机网络-第%202%20页%20的副本.drawio.png)

但是在传输过程中，**ACK7** 受到网络抖动，无法到达 发送方，发送方由于没有接收到 ACK，触发了超时重传，又将 $0\sim7$号的帧再次传了一遍，此时全部数据帧的序号虽然能对上，但完全不是一个周期的
___
现在我们将发送方的窗口大小变成 $2^3 - 1 = 7$ 看看，此时有  
![image](../images/计算机网络-第3页.drawio.png)

同样的，接收方收到第6号帧，进行累积确认，发送 **ACK6**，并将窗口滑动到第7号帧，有
![image](../images/计算机网络-第3页.2.drawio.png)

依旧收到网络抖动影响，发送方没有收到 **ACK6**  
触发超时重传后，发送方再次将 0 到 6 号的数据传输，此时与 接收方对应的 7 号帧不匹配  
此时接收方会重复发送最近一次正确接收帧的ACK，即 **ACK6**
___
可以看到，GBN协议中使用的是一个操蛋的 **累积确认**，错误就是来源于这个 累积确认

现在我们能确认的是，在回退N帧协议中，发送方窗口的大小 $\text{window(send)}$ 有一定的限制，为
$$
1 < \text{window(send)} \le 2^{\text{bit}} - 1
$$

#### 2.2.2 流水线模式2 —— 选择重传

选择重传 为了避免上述情况，是不会使用累积确认的，而是单独对每个帧进行确认

现在我们取 $\text{3}$ 位用作帧序号，序号从 $0$ 到 $2^{3} - 1$，一个循环共 $2^{3}$ 个帧  
我们假设发送方和接收方的窗口大小都为 $2^3 - 1 = 7$，在传输数据时，有
![image](../images/计算机网络-第%204%20页.drawio.png)

在返回 ACK 时，受到网络抖动，**ACK0** 没有传输到发送方，但是接收方的窗口已经移动，有  
![image](../images/计算机网络-第%204%20页.2.drawio.png)

待到触发超时重传后，发送方再次发送0号数据帧，接收方接收到并发散确认帧后，情况变为
![image](../images/计算机网络-第%204%20页.3.drawio.png)

整个传输过程可以顺利执行下去，但是数据已经出错

___

我们再尝试减少 发送方的窗口大小，最终在 $\text{window(send)} = 2^{\text{bit -1}}$ 时发现终于没有问题了  
现在我们能够确定
$$
\begin{aligned}
&1 < \text{window(send)} \le 2^{\text{bit - 1}}& \\
&1 < \text{window(recv)} \le \text{window(send)}&
\end{aligned}
$$

## 3. 交通事故处理

![image](../images/介质访问-交通事故处理.png)

### 3.1 CSMA/CD

#### 3.1.1 <span style="color: green">争用期，最小帧长</span>

虽然 交换机的出现已经把这种 总线型以太网 淘汰了，但是这个知识点考试还是会考，需要注意

![image](../images/csma-cd.png)

上图中，如果主机要发送数据到其他主机，数据流就像是一条 **蛇**，总线就像是一条 **管道**  
在 某一端的主机 发送数据/往管道里放蛇 的时候，其他主机不能发数据，怕有冲突  
在蛇 在 **整个管道** 里走一个来回 $2\tau$ 后，管道里才有机会空闲，其他主机才有机会发送数据，由此我们得出一个主机发送数据时的占用时间(<span style="color: red"> **争用期**</span>)为
$$
2\tau = 2 \times \frac{\text{length(pipe)}}{\text{speed(传输介质)}}
$$

并且，我们还发现，如果蛇太短了，主机放蛇之后就失去了对它的控制，需要让蛇的长度(**帧的长度**)刚好充满整个管道，计算得出
$$
\text{length(frame)} = \tau \times \text{speed(数据传输速率)}
$$
这就是 <span style="color: red">**最小帧长**</span>  
考虑到各个主机之间都要公平对待，都有机会发数据，因此协议中会规定一个 <span style="color: grey"> **最大帧长** </span>

#### 3.1.2 <span style="color: green"> 碰撞与退避算法</span>

好的，上述我们讨论了一些概念，这里再探讨总线上各个主机的行为  
在需要发送数据时，主机会监听信道，<span style="color: blue"> **一有空闲** </span>马上发送，其他主机发现没有空闲时，会一直监听，<span style="color: blue">直到 信道空闲，再发送</span>

___
但是我们要知道，碰撞检测不是一定能检测到所有碰撞的  
如果很不幸的发生了碰撞，主机会先退避一定时间，再尝试发送数据，直到判定网络出现故障，并汇报给主机程序  

具体一点的，主机遵循一定的退避算法 ———— 最多重复尝试发送次数 $\text{retry}$ 为 $16$ 次，<span style="color: green">随机退避时间</span> $t$ 与 退避次数 $k$ 的关系如下

$$
\begin{aligned}
&t = 2\tau \times \{0, 1, 3, \dots, 2^k - 1\}& \\
&k = \text{min}(\text{retry}, 10)& \\
\end{aligned}
$$
每次退避，$\text{retry}$ 都会自增

### 3.2 CSMA/CA

这是给无线网络的 随机介质访问，由于 <span style="color: red">**无线网络的物理性质** </span>，随着距离的扩大，信号衰减幅度会更大，远超过有线网络，使得无法有效检测碰撞，并且数据容易出错  
因此，**CSMA/CA**协议主要是为了 **Avoidence** —— 避免碰撞，而不是 **Detection** 检测碰撞  
同时，这种容易出错的环境 不适合 GBN 和 选择重传协议，因此在协议中使用 **停止-等待** 协议，尽量保证数据可靠

为了尽量避免碰撞产生，协议规定，<span style="color: green">**接入设备**</span> 在发送数据前，都要等待 **DIFS** 时间，高优先级数据 只需等待 **SIFS** 时间  
这个等待时间，不仅是为了尽量避免碰撞，由于无线信号容易被干扰，给出一定时间 可以用作 **差错检测**  

当 接收端 检测到 数据报有错误时，对这个数据报 <span style="color: blue">不进行处理，也不发送 ACK</span>，发送端没有接收到 ACK，判定数据报 超时，进行 **超时重传**，不过 <span style="color: green">接入设备</span>进行重传时， 也要先等待 **DIFS**

![image](../images/csma-ca.png)

#### 3.2.1 退避算法

在需要发送数据时

1. 若主机检测到 信道空闲，等待 **DIFS** 后，再发送
2. 若主机检测到 信道不空闲，需要使用 **CA** 的退避算法，退避完成后，再发送数据

**CA** 的退避算法，具体为

1. 设置一个 随机退避时间 $duration$
2. 监听信道，信道为空闲时，$duration$ 启动倒计时

```kotlin
var duration: Int = ...
while (true) {
    if (duration == 0) {
        break // 退避完成
    }

    if (isSpace) { // 如果空闲
        duration -= 1
    }
}
```

由于检测不到碰撞，各个主机之间 通过 数据报 **超时** 来判定有 **碰撞或差错产生**

#### 3.2.2 隐蔽站问题

由于无法检测到碰撞，不能像 有线总线型网络 中那样能够检测到所有主机的碰撞，会出现 **隐蔽站** 的问题，协议中给出了 **预约** 的解决方法，即

1. 主机要发送数据前，根据协议先等待 **DIFS** ，再发送 **RTS (Request To Send)** 帧
2. 无线接入点(AP) 准备好接收后，准备**广播** 高优先级的 **CTS (Clear To Send)** 帧，根据协议 等待 **SIFS** 时间
3. RTS 告诉 AP 谁要进行数据传输，和传输的时间
4. CTS 告诉 网络中的所有节点，谁要进行数据传输 和 其占用时间，其他节点 在这个占用时间内不要对 AP 有访问
5. 传输完成后，AP 站点广播 **ACK** ，告知其他站点也可以进行传输了

![image](../images/csma-ca.2.drawio.png)

#### 3.3.3 <span style="color: green">补充</span>

协议中有三种 IFS (inter-frame space，帧间隔)，其中有

1. **DIFS** Distributed Inter Frame Space，最长的IFS
2. **PIFS** Point Inter Frame Space，中等长度 IFS
3. **SIFS** Short Inter Frame Space，最短的IFS

**SIFS** 用作高优先的帧，有

1. CTS
2. ACK
3. 对 AP 的应答帧
4. 分片后的数据帧/尽快处理完

并且，信道中的节点争取到 争用窗口后，为了保证数据连贯性，都会等待 SIFS 后，传输数据

**再次补充**  
CSMA/CA 中没有规定 最小帧长 和 最大帧长

### 4.1 奇偶校验

这个方式专门对 <span style="color: red">**1的个数**</span> 进行校验  
将原始数据加工成

1. 校验结果
2. 原始数据

后，整体的1的个数要符合 校验标准

在进行 <span style="color: green"> **奇校验** </span>时  
当发现数据中1的个数是奇数，加上校验结果，要使整体1的个数为奇数，所以校验结果为 0；  
当发现数据中1的个数是偶数，加上校验结果，要使整体1的个数为奇数，所以校验结果为 1

在进行 <span style="color: green"> **偶校验** </span> 时  
当发现数据中1的个数是奇数，加上校验结果，要使整体1的个数为偶数，所以校验结果为 1；  
当发现数据中1的个数是偶数，加上校验结果，要使整体1的个数为偶数，所以校验结果为 0

___
但是这种方式的检错能力有限，如果有偶数个错误尝试，无法检出，也不能判断有多少个错误
